# CJM жизненного цикла мероприятия

> Сквозные customer journey maps ведения мероприятия — от появления до закрытия.
> Два взгляда: **менеджер** (владелец меро, от внешней заявки до закрытия и простановки часов)
> и **тим-лидер** (от назначения до закрытия меро менеджером).
>
> Формат: этап → действие/точка входа → система/результат → эмоции/риски.
> Роли и права — [access-control.md](access-control.md); данные — [db.md](db.md);
> пошаговые кейсы — [user-journeys-web.md](user-journeys-web.md), [user-journeys-bot.md](user-journeys-bot.md);
> отчёты — [reports.md](reports.md).
>
> Легенда: 🟢 happy-path · ⚠️ риск/развилка · 🔗 связь с другой ролью.

## Часть 1. CJM менеджера — от внешней заявки до закрытия меро

Контекст: во внешний источник (почта, звонок, Добро.ру, партнёрская организация) пришла
заявка на волонтёрскую помощь. Менеджер заводит меро в системе и ведёт его до конца.

### Этап 0. Входящий запрос извне (вне системы)

| | |
|---|---|
| **Действие** | Организатор/партнёр присылает запрос: нужна помощь N волонтёров, дата, задачи. |
| **Система** | Ещё не задействована. Менеджер фиксирует договорённости. |

### Этап 1. Проверка/заведение организации и организатора

| | |
|---|---|
| **Точка входа** | `Организации` (`/organizations/`), `Организаторы` (`/organizers/`). |
| **Действие** | Найти существующую организацию/контакт или создать новые (CRUD). Привязать организатора к организации. |
| **Система** | `organizations`, `organizers`, `organizer_organization_link`. История общения → `organizer_interaction_log`. |
| **Права** | Только менеджер (ACL A-10). |
| **Эмоции/риски** | 🟢 Единый справочник контактов. ⚠️ Дубли организаций — проверять перед созданием. |

### Этап 2. Создание мероприятия (черновик)

| | |
|---|---|
| **Точка входа** | `Мероприятия` → `Создать` (`/events/new/`) — веб-журней M2. |
| **Действие** | Заполнить: название, описание, локация, организация/организатор, **категории** (выпадающий список), ссылки (чат, пост, Добро.ру), **тип учёта Добро.ру**. |
| **Тип учёта Добро.ру** | `none` (часы на Добро.ру не ведём) · `shared` (выбрать общую ссылку `dobro_ru_shared_links` — для мелких меро) · `unique` (ввести свою ссылку — для крупных, напр. ДОД). См. db.md правило 7e. |
| **Система** | `events` (event_status='upcoming', recruit_status='open'), `event_category_map`. |

### Этап 3. Настройка дней, набора и требований

| | |
|---|---|
| **Действие** | Добавить дни (`/events/<id>/days/add/`): дата, время, `volunteer_needed`, локация. Задать требования (`event_requirements`) и, при необходимости, исключения. |
| **Система** | `event_days`, `event_requirement_map`. Порог набора считается как `recruit_close_ratio × SUM(volunteer_needed)`. |
| **Эмоции/риски** | ⚠️ `volunteer_needed` влияет на авто-закрытие набора — задать аккуратно. |

### Этап 4. Назначение персонала

| | |
|---|---|
| **Действие** | Назначить тим-лидера(ов) и, при необходимости, со-менеджеров (`/events/<id>/staff/assign/`). |
| **Система** | `event_staff` (staff_role='team_lead). |
| 🔗 | С этого момента у ТЛ начинается его CJM (Часть 2). |

### Этап 5. Публикация и анонс

| | |
|---|---|
| **Действие** | `Опубликовать` (`/events/<id>/publish/`). |
| **Система** | `published_at`; диспетчер `broadcast_new_event` шлёт анонс подписанным волонтёрам (только `notify_new_events=true`). |
| **Эмоции/риски** | 🟢 Меро видно в ленте и боте. ⚠️ Публикация — только Web/Mini App, в боте её нет. |

### Этап 6. Набор: приём и обработка заявок

| | |
|---|---|
| **Действие** | Заявки поступают от волонтёров (бот/веб) и/или импортируются из Excel (`/applications/import/`). Менеджер/ТЛ одобряют или отправляют в резерв. |
| **Система** | `applications` (new→approved/rejected); при approve — авто-`participations` на все дни; пересчёт `recruit_status`. Уведомления волонтёрам. |
| **Мониторинг** | Внутренняя карточка меро: нужно/есть/осталось, список заявок с фильтрами. |
| **Эмоции/риски** | ⚠️ Перебор заявок (> нужно×1.2−набрано) → массовые действия с выбором (вручную / все / в порядке поступления). ⚠️ Недобор → добор из резерва (rejected→approved). |

### Этап 7. Проведение меро (день X)

| | |
|---|---|
| **Действие** | Меро идёт; на месте работает ТЛ. Менеджер подстраховывает (может обрабатывать заявки/явку на любом меро). |
| **Система** | `event_status`: upcoming→ongoing по времени. |
| 🔗 | Явку ставит ТЛ (Часть 2, этап 4) — менеджер может вмешаться. |

### Этап 8. Явка и закрытие смены

| | |
|---|---|
| **Действие** | Проставляется явка (attended / absent_excused / absent_unexcused), часы, полная смена. Ввести **обязательное** `people_helped`. |
| **Система** | `participations`; пересчёт статистики волонтёров и churn; `event_status`→finished. |
| **Эмоции/риски** | ⚠️ Без `people_helped` меро не закрыть (правило 7). ⚠️ Неявки → churn, при пороге — блэклист (не озвучивается). |

### Этап 9. Простановка часов на Добро.ру 🔗 ключевой отчёт

| | |
|---|---|
| **Точка входа** | `Отчёты` → `Часы на Добро.ру` (`/reports/dobro/`) — журней M17, отчёт reports §8. |
| **Действие** | Открыть отчёт за период. Выбрать удобный разрез: **по человеку** (идти по волонтёрам) или **по ссылке** (открыть одну ссылку Добро.ру и закрыть всех). Проставить часы на сайте Добро.ру и **отметить** факт в системе. |
| **Система** | `participations.dobro_ru_logged` (+logged_at/by); при полном закрытии — `events.dobro_ru_hours_logged=true`. |
| **Удобство** | Шапка показывает: сколько участий к простановке, сколько закрыто, сколько меро исключено (`none`), незакрытые ссылки. |
| **Эмоции/риски** | 🟢 Ничего не забыто — прогресс по каждой ссылке виден. ⚠️ Меро с `none` намеренно вне отчёта. |

### Этап 10. Пост-меро: письма, рейтинг, оценка организации

| | |
|---|---|
| **Действие** | Через `feedback_delay_hours` волонтёрам уходит просьба оценить меро. Менеджер/ТЛ при желании ставят рейтинг/комментарий организации. Волонтёры скачивают благодарственные письма (если задан `letter_id`). |
| **Система** | `event_feedbacks`, `organizations.internal_rating/comment`, генерация письма на лету. |
| **Эмоции/риски** | 🟢 Обратная связь копится для отчётов и истории организации. |

### Этап 11. Аналитика и отчётность

| | |
|---|---|
| **Действие** | Меро попадает в отчёт за период (`/reports/period/`): часы, воронка, эффективность набора, проблемные зоны. Экспорт Excel/PDF/комплексный. |
| **Система** | Агрегаты по `participations`, `applications`, `events`. |
| **Эмоции/риски** | 🟢 Цикл закрыт: от внешней заявки до отчётности перед руководством/грантодателями. |

**Итоговая нить менеджера:** внешний запрос → организация/организатор → черновик меро (+тип Добро.ру)
→ дни/набор/требования → назначение ТЛ → публикация/анонс → обработка заявок → проведение →
явка + people_helped → **простановка часов на Добро.ру** → письма/оценки → отчётность.

## Часть 2. CJM тим-лидера — от назначения до закрытия меро менеджером

Контекст: менеджер назначил волонтёра тим-лидером на конкретное меро (этап 4 выше).
Права ТЛ **контекстны** — только это меро, пока оно не завершено.

### Этап 0. Назначение

| | |
|---|---|
| 🔗 | Менеджер создаёт запись `event_staff(staff_role='team_lead')` — Часть 1, этап 4. |
| **Система** | В боте/вебе у ТЛ появляется меро в разделе `👥 Мои мероприятия (ТЛ)` (bot TL1) / внутренняя карточка (web TL1). |
| **Эмоции/риски** | 🟢 ТЛ видит только свои меро. ⚠️ Уведомление о назначении — по политике (если включено). |

### Этап 1. Знакомство с мероприятием

| | |
|---|---|
| **Точка входа** | Бот: `/myevents` → `[Открыть]` (TL1a). Веб: внутренняя карточка меро (TL1). |
| **Действие** | Изучить подробную карточку: название, описание, контакты организатора (Telegram + телефон), ФИО, набор — нужно/есть/осталось. |
| **Система** | Чтение `events`, `event_days`, `organizers`, агрегатов набора. |
| **Эмоции/риски** | 🟢 Вся операционная информация в одном месте. |

### Этап 2. Настройка уведомлений и требований

| | |
|---|---|
| **Действие** | При желании включить/выключить уведомления о заявках (`notify_applications`, bot TL9). Задать/уточнить требования и исключения по своему меро (web TL8). |
| **Система** | `users.notify_applications`, `event_requirements`, `user_requirement_exceptions`. |
| **Эмоции/риски** | ⚠️ Отключив уведомления, ТЛ должен сам заходить в раздел заявок. |

### Этап 3. Обработка заявок (набор)

| | |
|---|---|
| **Точка входа** | Уведомление о новой заявке (TL2) или карточка меро → список заявок. |
| **Действие** | Одобрять / отправлять в резерв поштучно (TL3) или массово (TL4). Смотреть профиль кандидата в контексте (TL5). Оставлять внутренние комментарии (TL7). |
| **Система** | `applications` (new→approved/rejected), авто-`participations` при approve, пересчёт `recruit_status`, `user_comments`. |
| **Эмоции/риски** | ⚠️ Перебор заявок → предупреждение и выбор стратегии (вручную / все / в порядке поступления, TL4). ⚠️ Доступ к профилю кандидата пропадает после завершения меро (правило 5). |

### Этап 4. Проведение и простановка явки

| | |
|---|---|
| **Точка входа** | Карточка меро/дня → экран явки (bot TL6 / web TL3). |
| **Действие** | По каждому участнику: `Был` (attended) / `Уваж.` (absent_excused) / `Неявка` (absent_unexcused); отметить `Полную смену`; проставить/уточнить часы. |
| **Система** | `participations.status/full_shift/hours`; пересчёт статистики и churn волонтёров. |
| **Эмоции/риски** | ⚠️ Неявка без предупреждения → churn волонтёру (при пороге — блэклист, статус не озвучивается). ⚠️ Явку нельзя ставить раньше дня меро (политика POL-05). |

### Этап 5. Фиксация результатов меро

| | |
|---|---|
| **Действие** | Внести `people_helped` (обязательно), внутренние заметки по организации меро. При необходимости — рейтинг/комментарий организации (после проведённого меро, TL7 web). |
| **Система** | `events.people_helped`, `events.internal_comment`, `organizations.internal_rating/comment`. |
| **Эмоции/риски** | ⚠️ Без `people_helped` меро не закрывается. |

### Этап 6. Передача менеджеру и закрытие

| | |
|---|---|
| 🔗 | Часы/явка проставлены ТЛ → менеджер закрывает меро (`event_status='finished'`) и проставляет часы на Добро.ру (Часть 1, этапы 8–9). Простановка на Добро.ру — **зона менеджера**, не ТЛ. |
| **Система** | После `finished` контекстные права ТЛ на это меро прекращаются (правило 5): доступ к расширенным/внутренним профилям кандидатов закрывается. |
| **Эмоции/риски** | 🟢 ТЛ завершил операционную часть. ⚠️ После закрытия ТЛ видит меро как обычный волонтёр (публичная карточка). |

### Этап 7. После закрытия

| | |
|---|---|
| **Действие** | ТЛ может оценить меро как участник (если участвовал), видит своё меро в публичной истории; его счётчики «меро как ТЛ» растут. |
| **Система** | `team_leaders.total_events/season_events`, `event_feedbacks`. |
| **Эмоции/риски** | 🟢 Вклад ТЛ зафиксирован в его профиле (публичные доп. поля ТЛ). |

**Итоговая нить тим-лидера:** назначение → знакомство с меро → настройка уведомлений/требований
→ обработка заявок (набор) → явка + полная смена + часы → people_helped/заметки →
передача менеджеру (Добро.ру — на менеджере) → закрытие меро → потеря контекстных прав →
меро в публичной истории ТЛ.

## Стык ролей (кто за что отвечает)

| Действие | Менеджер | Тим-лидер |
|---|---|---|
| Заведение организации/организатора | ✓ | ✗ |
| Создание/публикация меро, тип Добро.ру | ✓ | ✗ |
| Назначение ТЛ | ✓ | ✗ |
| Обработка заявок | ✓ (все меро) | ✓ (своё меро) |
| Простановка явки/часов/полной смены | ✓ (все) | ✓ (своё) |
| `people_helped` | ✓ | ✓ (своё) |
| **Простановка часов на Добро.ру** | ✓ | ✗ (зона менеджера) |
| Закрытие меро (`finished`) | ✓ | ✗ |
| Рейтинг/комментарий организации | ✓ (в любой момент) | ✓ (после своего меро) |
| Отчётность за период | ✓ | ✗ |
