# Миграция легаси-данных и сопоставление профилей с Telegram

> **Назначение:** описание процесса загрузки исторических («легаси») данных ВЦ —
> нескольких тысяч мероприятий и участий, часть информации по которым утеряна, — в
> текущую систему, а также механики надёжного сопоставления (identity resolution)
> реального человека в системе с его Telegram-аккаунтом, когда ФИО, телефон и TG-username
> ненадёжны (дублируются, меняются, отсутствуют).
>
> Документ — **проектное решение**, а не готовый код. Он задаёт форматы входных таблиц,
> правила матчинга и порядок обработки так, чтобы реализацию можно было отдать младшему
> исполнителю без домысливания.
>
> Опирается на: [db.md](db.md) (правила 5 и 8, схема `users`/`participations`/`events`),
> [import_applications.py](../blog/services/import_applications.py) (существующий Excel-импорт
> заявок — переиспользуем его подход к превью/dedup), [applications.py](../blog/services/applications.py)
> (`find_matching_user`), [tg-bot.md](tg-bot.md) §3 (первое касание, `telegram_id` как
> идентичность).

## 0. Ключевые принципы (прочитать до реализации)

1. **`telegram_id` — единственный первичный источник идентичности.** Аккаунт «настоящий»
   тогда и только тогда, когда у него есть числовой `telegram_id` (db.md, правило 8).
   Легаси-данные Telegram-аккаунта **не** содержат — там есть только ФИО / телефон /
   @username, которые ненадёжны. Поэтому легаси-профиль — всегда «неполноценный» до момента,
   пока живой человек не подтвердит его собой через `/start` в боте.

2. **Мы не выдумываем людей.** Легаси-участник, которого не удалось уверенно сопоставить с
   существующим профилем, **не превращается в запись `users`**. Он лежит в staging-таблицах
   и ждёт, пока соответствующий человек сам придёт в бота. Это осознанное решение заказчика:
   лучше временно «подвешенная» история, чем тысячи призрачных профилей-дублей.

3. **Матчинг ~90% автоматический.** Есть чёткий, конечный список условий, при которых мы
   уверены на 100% и сливаем автоматически (§4.1). Всё, что вне этого списка, — в очередь
   ручной проверки (§4.2). Ошибка «слить двух разных людей в один аккаунт» необратима и
   недопустима, поэтому при малейшей неоднозначности — руки оператора.

4. **Нельзя влить нового пользователя в старый аккаунт.** Отдельный, не менее важный риск,
   чем ложное слияние легаси: когда в бота приходит **новый** человек, случайно похожий на
   легаси-запись (тёзка), нельзя отдать ему чужую историю. Правила §4 симметрично защищают
   от обоих направлений ошибки.

5. **Импорт идемпотентен.** Повторная загрузка того же файла не создаёт дублей — у каждой
   легаси-строки есть стабильный `source_row_id` (см. §2.3), по которому распознаётся
   повторная загрузка. Тот же принцип уже применён в
   [import_applications.py](../blog/services/import_applications.py) (`_application_dedup_key`).

Легаси загружается **один раз** большим батчем (bulk). После него система живёт в обычном
режиме, а «хвост» несопоставленных легаси-записей постепенно рассасывается за счёт §5 —
по мере того как живые люди приходят в бота.

## 2. Форматы экспортных таблиц

Оператор сводит легаси в **две** плоские таблицы (CSV UTF-8 или XLSX). Обе допускают
пропуски — часть информации утеряна, и это ожидаемо. Обязательные поля отмечены **жирным**;
остальные могут быть пустыми.

### 2.1 Таблица A — `legacy_events.csv` (мероприятия)

Одна строка = одно легаси-мероприятие.

| Колонка | Обяз. | Тип | Комментарий | Целевое поле |
|---|---|---|---|---|
| `source_event_id` | **да** | строка | Стабильный ключ мероприятия в легаси (любой уникальный идентификатор оператора: номер строки в исходнике, дата+название и т.п.). Нужен для связи с таблицей B и идемпотентности | — (staging) |
| `title` | **да** | строка | Название | `events.title` |
| `description` | нет | текст | Описание | `events.description` |
| `team_leader_tg` | нет | строка | Тим-лидер **как ссылка на его TG** (`@username` или `t.me/...`). Именно ссылка, а не ФИО — так надёжнее сопоставить с профилем ТЛ | → `event_staff` (staff_role=`team_lead`) после резолва TG в `users` |
| `shifts` | нет | текст | Смены в человекочитаемом виде (даты/время «12.07.2026 10:00–14:00; 13.07…»). Разбор — best-effort (§2.4) | `event_shifts` |
| `tg_post_link` | нет | URL | Ссылка на пост в канале | `events.post_in_chanel_link` |
| `dobro_ru_link` | нет | URL | Ссылка на Добро.ру | `events.dobro_ru_link` (+ `dobro_ru_link_kind='unique'`) |
| `location` | нет | строка | Локация (текст, резолвится в `locations` по имени) | `events.location_id` |
| `organization` | нет | строка | Организация (текст) | `events.organization_id` (по имени, get-or-create) |
| `event_date` | нет | дата | Опорная дата, если `shifts` не разобрать — из неё делаем одну смену | `event_shifts.day` |

**Обработка утерянных данных.** Если у мероприятия нет ни `shifts`, ни `event_date` — оно
создаётся **без смен** и помечается флагом `needs_review` (см. §2.4). Такое мероприятие уже
существует в системе (в него можно записывать участия), но менеджеру видно, что даты нужно
восстановить вручную. Мероприятие без дат **не** ломает `Event.compute_status()` — тот
корректно возвращает хранимое `event_status` при пустом наборе смен
([models.py](../blog/models.py) `compute_status`).

### 2.2 Таблица B — `legacy_participation.csv` (кто в каком меро участвовал)

Одна строка = один факт «человек X участвовал в меро Y и получил N часов». **Без разбивки
по конкретным сменам** — как и договорено, легаси хранит только суммарные часы за меро, что
тривиально ложится в нашу модель (одна смена → одно `participations` с этими часами).

| Колонка | Обяз. | Тип | Комментарий | Целевое поле |
|---|---|---|---|---|
| `source_event_id` | **да** | строка | Ссылка на `legacy_events.source_event_id` | связь с меро |
| `full_name` | **да** | строка | ФИО одной строкой (или см. `first_name`/`last_name`) | `first_name`/`last_name` |
| `first_name` | нет | строка | Если ФИО разложено | `users.first_name` |
| `last_name` | нет | строка | | `users.last_name` |
| `tg_username` | нет | строка | `@username` на момент участия (мог смениться!) | ключ матчинга (§4) |
| `phone` | нет | строка | Телефон (мог смениться!) | ключ матчинга (§4) |
| `hours` | нет | число | Суммарные отработанные часы за это меро. Пусто → 0 | `participations.hours` |
| `participation_date` | нет | дата | Дата участия, если известна (уточняет, в какую смену писать) | — |

> **Почему ФИО обязательно, а TG/телефон — нет.** ФИО есть почти всегда (это тот минимум,
> что фиксировался в чатах/таблицах). TG-username и телефон часто утеряны или устарели.
> Но именно поэтому **одного ФИО недостаточно для автоматического слияния** (§4) — тёзки.

### 2.3 Стабильные ключи и идемпотентность

- `source_event_id` в таблице A **уникален** в пределах файла. Дубли → ошибка валидации.
- Каждая строка таблицы B получает вычисляемый `source_row_id = hash(source_event_id +
  full_name + tg_username + phone + hours)`. По нему при **повторной** загрузке того же файла
  строка распознаётся как уже загруженная и пропускается (аналогично `seen_keys` в
  [import_applications.py](../blog/services/import_applications.py) `commit_import`).
- Оба ключа сохраняются в staging (§3), чтобы миграцию можно было прогонять частями и
  повторно, не боясь дублей.

### 2.4 Best-effort разбор смен и флаг `needs_review`

Колонка `shifts` — свободный текст. Парсер пытается вытащить даты/интервалы; всё, что не
удалось распарсить, **не отбрасывается**, а мероприятие помечается `needs_review=true` с
человекочитаемым `review_reason` («не удалось разобрать смены: <исходный текст>»). Менеджер
видит очередь `needs_review` в вебе и правит вручную. Никакой парсер не должен **терять**
данные молча — либо разобрал, либо явно пометил на ревью.

## 3. Staging-слой (промежуточное хранилище)

Легаси **не** пишется сразу в боевые `users`/`events`/`participations`. Сначала — в
отдельные staging-таблицы (новое приложение `legacy` или префикс `legacy_` в существующем).
Это даёт: возможность прогонять матчинг многократно без порчи боевых данных, аудит
(«откуда взялось это участие»), и «подвешенное» хранение несопоставленных людей (принцип 2).

Минимальный набор staging-таблиц:

| Таблица | Смысл |
|---|---|
| `legacy_event` | Сырые строки таблицы A + `needs_review`, `review_reason`, `resolved_event_id` (FK на созданный `events`, NULL пока не создан) |
| `legacy_person` | Уникальные люди из таблицы B (свёрнутые по нормализованному ключу, §4.0). Хранит нормализованные ФИО/tg/phone, `match_status`, `resolved_user_id` (FK на `users`, NULL пока не сопоставлен) |
| `legacy_participation` | Строки таблицы B: `legacy_person` × `legacy_event` × `hours`. Именно отсюда после резолва создаются боевые `participations` |
| `legacy_match_candidate` | Для строк, ушедших в ручную проверку: `legacy_person` × кандидат-`users` × `score` × причина. Оператор выбирает из этого списка |

`match_status` у `legacy_person`: `unmatched` (ждёт §5) · `auto_matched` · `manual_pending`
(в очереди §4.2) · `manual_matched` · `manual_new` (оператор решил «это новый человек, не в
боте — оставить в staging»).

## 4. Правила сопоставления (identity resolution)

Это ядро документа. Задача: для легаси-человека найти **тот же самый** реальный человек среди
`users`, не слив разных людей и не влив нового человека в чужую историю.

### 4.0 Нормализация (до любого сравнения)

Все ключи приводятся к каноническому виду, иначе сравнение бессмысленно:

- **ФИО:** trim, схлопывание пробелов, lower-case, снятие `ё→е`. Сравнение по паре
  (`first_name`, `last_name`) — как в [applications.py](../blog/services/applications.py)
  `find_matching_user` (шаг 3). Отчество, если есть, хранится, но в ключ матчинга по
  умолчанию не входит (часто отсутствует).
- **TG-username:** снять ведущий `@` и хвост `t.me/`, lower-case. Точно как
  `telegram_username.lstrip('@')` + `__iexact` в существующем матчинге.
- **Телефон:** оставить только цифры, привести `8XXXXXXXXXX` → `7XXXXXXXXXX`, взять
  последние 10 цифр как канон (защита от `+7`/`8`/пробелов/скобок).

> **Важно про `telegram_id`.** В легаси его нет. Поэтому «сопоставить по `telegram_id`» на
> этапе миграции **невозможно** — он появляется только когда человек приходит в бота (§5).
> На этапе §4 мы работаем исключительно с ненадёжными ключами: username / телефон / ФИО.

### 4.1 Условия АВТОМАТИЧЕСКОГО слияния (100% уверенность)

Автослияние легаси-персоны с существующим `users` допускается **только** если выполнено
одно из сочетаний ниже **И** кандидат в `users` при этом **ровно один** (см. §4.4 про
уникальность). Логика — «два независимых ненадёжных признака, совпавшие вместе, дают
надёжность»:

| # | Совпало | Почему 100% | Комментарий |
|---|---|---|---|
| A1 | **ФИО** (норм.) **+ TG-username** (норм.) | Тёзка с тем же @username — практически невозможно: username в Telegram уникален глобально | Основной сценарий. Если username сменился — этот путь не сработает, уйдём в A2/ручную |
| A2 | **ФИО** (норм.) **+ телефон** (норм.) | Тёзка с тем же номером — практически невозможно | Работает, даже если username утерян/сменился |
| A3 | **TG-username + телефон** (оба норм., ФИО расходится) | Два уникальных технических идентификатора на одном человеке | Редкий, но валидный кейс: ФИО записали с ошибкой/девичья фамилия, а @username и номер те же |

**Только совпадение по одному ключу — НЕ основание для автослияния:**

- только ФИО → тёзки (заказчик явно указал: ФИО дублируется у разных людей) → **ручная проверка**;
- только TG-username → у существующего профиля username мог смениться, а на этот @username
  мог сесть **другой** человек (Telegram переиспользует освободившиеся username) → **ручная проверка**;
- только телефон → номер мог быть переоформлен на другого человека → **ручная проверка**.

Порядок проверки (первое сработавшее сочетание побеждает): **A1 → A2 → A3**. Он совпадает с
приоритетом существующего `find_matching_user` (username → phone → ФИО), только ужесточён
требованием **двух** совпавших признаков вместо одного.

### 4.2 Условия РУЧНОЙ проверки

Легаси-персона уходит в очередь `legacy_match_candidate` (оператор решает вручную), если:

1. Совпал **ровно один** ключ (только ФИО / только username / только телефон) — см. выше.
2. Сработало сочетание из §4.1, но **кандидатов в `users` больше одного** (например, два
   реальных Ивановых Иванов, оба без телефона в профиле, а у легаси-строки только ФИО+username,
   и username совпал у обоих — маловероятно, но обрабатываем безопасно). §4.4.
3. «Почти совпадение» (fuzzy): ФИО различается на 1–2 символа (расстояние Левенштейна ≤ 2) при
   совпавшем втором ключе, либо телефон отличается на одну цифру. Это **не** автослияние —
   подсвечиваем оператору как вероятного кандидата с пометкой «возможна опечатка» (db.md
   правило 5 прямо требует проверять опечатки, чтобы не плодить дубли).

Оператор в очереди по каждой легаси-персоне выбирает одно из:
**«слить с профилем X»** · **«это новый человек (оставить в staging, ждать бота)»** ·
**«пропустить/мусор»**.

### 4.3 Нет ни одного кандидата → НЕ создаём профиль

Если для легаси-персоны в `users` нет **ни одного** кандидата ни по одному ключу — по решению
заказчика профиль **не создаётся**. Персона остаётся в `legacy_person` со статусом `unmatched`,
её `legacy_participation` висят непривязанными. Они «оживут» позже через §5, когда/если этот
человек придёт в бота. Если не придёт никогда — история просто не будет ему начислена, и это
приемлемо.

### 4.4 Защита от ложного слияния (симметрично в обе стороны)

Ключевое требование заказчика — **не влить разных людей в один аккаунт** и **не влить нового
пользователя в старый аккаунт**. Реализуется двумя правилами:

1. **Уникальность кандидата.** Автослияние (§4.1) выполняется, только если совпавшему сочетанию
   удовлетворяет **ровно один** `users`. Если несколько — всегда ручная проверка, даже при
   «сильном» сочетании. `.first()` из существующего `find_matching_user` для миграции
   **недопустим** — берём весь список кандидатов и считаем их количество.
2. **Направление слияния фиксировано: легаси → существующий боевой профиль.** Мы никогда не
   «переносим» боевой профиль в легаси-запись и не переписываем его `telegram_id`. Легаси лишь
   **дополняет** существующий профиль историей (`participations`), не трогая идентичность,
   `telegram_id`, роли и веб-креды боевого аккаунта.

## 5. Отложенный матчинг: связывание человека с TG при `/start`

Это механизм, который «рассасывает» несопоставленный легаси-хвост (§4.3) и корректно
привязывает Telegram-аккаунт к исторической личности **в момент, когда человек сам приходит**.
Именно здесь появляется недостающий `telegram_id`.

### 5.1 Триггер

При первом касании (`/start`, tg-bot.md §3.1) после создания/нахождения `users` по
`telegram_id` система дополнительно запускает поиск по `legacy_person` со статусом `unmatched`
(или `manual_new`), используя **те же признаки, что теперь есть у живого аккаунта**: его
`telegram_username`, а после регистрации (tg-bot.md §3.2) — введённые ФИО и телефон.

### 5.2 Правила привязки (те же уровни уверенности, что §4.1)

Теперь у нас на руках **надёжный** `telegram_id` живого человека плюс его актуальные
username/ФИО/телефон. Сопоставляем их с легаси-персонами:

| Ситуация | Действие |
|---|---|
| Легаси-персона однозначно совпала по §4.1-сочетанию (ФИО+username, ФИО+телефон, username+телефон), кандидат один | **Авто-привязка:** `legacy_person.resolved_user_id = <этот user>`, переносим `legacy_participation` → боевые `participations`, пересчитываем агрегаты (`total_hours`, `total_event_count` — db.md правило 1) |
| Совпал только один ключ / несколько легаси-кандидатов / fuzzy | **Не привязываем молча.** Кладём в ту же очередь ручной проверки (§4.2) для менеджера. Человеку в боте историю пока не показываем |
| Совпадений нет | Ничего — это просто новый волонтёр без легаси-истории. **Важно: не подсовываем ему чужую историю** (принцип 4) |

### 5.3 Защита «новый человек ≠ старый аккаунт»

Поскольку в §5 мы стартуем от **надёжного** `telegram_id`, риск «влить нового в старого»
сводится к тому же правилу двух признаков: новый Вася Тёзкин получит легаси-историю другого
Васи Тёзкина, только если у них совпал **второй** независимый признак (телефон или username) —
что означает, что это с высокой вероятностью один человек. При совпадении лишь по ФИО —
уходим в ручную проверку, а не привязываем. Так тёзка не заберёт чужие часы автоматически.

### 5.4 Перенос истории (что происходит при успешной привязке)

1. `legacy_person.resolved_user_id` ← id боевого `users`; `match_status='auto_matched'`.
2. Для каждой `legacy_participation` этой персоны:
   - находим/создаём боевое `events` (из `legacy_event.resolved_event_id`; если меро ещё не
     материализовано — материализуем его из `legacy_event`, §2.1);
   - обеспечиваем наличие хотя бы одной `event_shifts` (из `shifts`/`event_date`; если дат нет
     — одна «синтетическая» смена-контейнер, чтобы было к чему привязать участие);
   - создаём `participations(user, event_day=shift, hours, status='attended')` — `get_or_create`,
     чтобы повторный прогон не задваивал (idempotent).
3. Пересчитываем кэш-агрегаты пользователя (db.md правило 1). Churn по легаси **не** начисляем —
   исторические неявки не реконструируем, стартуем с чистого `churn_score`.

## 6. Синхронизация легаси с текущими данными

Отдельная задача — легаси может **пересекаться** с уже существующими в системе данными (меро
и участия, заведённые вручную или через обычный Excel-импорт заявок до миграции).

### 6.1 Мероприятия

- Сопоставление легаси-меро с существующим `events` — по нормализованному `title` **+**
  пересечению дат (`event_shifts.day`). Только совпадение названия — недостаточно (бывают
  ежегодные одноимённые меро) → при совпадении названия, но расхождении дат создаётся **новое**
  мероприятие.
- Точное совпадение (название + дата) → легаси **дополняет** существующее меро недостающими
  полями (описание, ссылки, ТЛ), **не перезатирая** уже заполненные значения. Пустое в системе +
  заполненное в легаси → берём легаси; заполнено в обоих → оставляем систему, а расхождение
  пишем в `internal_comment` для ручной сверки.

### 6.2 Участия

- Дубль участия (`user` × `event`) определяется после резолва персоны и меро. Если боевое
  `participations` для этой пары уже есть — легаси-часы **не** задваиваются. Политика по
  умолчанию: **макс. из двух** значений часов (легаси часто полнее, но и введённое вручную не
  затираем занижением), расхождение — в лог сверки. Значение политики вынести в `const`
  (напр. `legacy_hours_conflict='max'|'keep'|'legacy'`), чтобы менять без кода.

### 6.3 Тим-лидеры и организаторы из легаси

- `team_leader_tg` резолвится в `users` по TG-username (§4.0). Если ТЛ найден — создаём
  `event_staff(staff_role='team_lead')` и, при отсутствии активной роли, запись в `team_leaders`.
  Если ТЛ по username не найден — **не создаём** призрачного ТЛ (принцип 2), помечаем меро
  `needs_review` с исходной TG-ссылкой.
- Организации/организаторы из легаси — get-or-create по нормализованному имени; при
  неоднозначности — `needs_review`, а не автосоздание дубля.

## 7. Порядок реализации (для исполнителя)

1. **Staging-модели** (§3) + миграция схемы. Ничего не трогает в боевых таблицах.
2. **Парсер+валидатор** двух CSV/XLSX (§2) → заполнение `legacy_event`/`legacy_person`/
   `legacy_participation`. Здесь же — нормализация (§4.0), `source_row_id`, `needs_review`.
   Переиспользовать подход `parse_excel`/`commit_import` из
   [import_applications.py](../blog/services/import_applications.py).
3. **Матчер** (§4): по каждой `legacy_person` считает кандидатов, проставляет `match_status`,
   наполняет `legacy_match_candidate`. Чистая функция «персона → (решение, кандидаты)» —
   легко покрыть юнит-тестами на кейсах A1–A3, тёзки, опечатки.
4. **Материализация** авто-сматченного (§5.4) и §6-синхронизация в боевые таблицы —
   в одной транзакции на персону, `get_or_create` везде.
5. **Веб-очередь ручной проверки** (§4.2) для менеджера: список кандидатов со score, кнопки
   «слить / новый / пропустить»; и очередь `needs_review` по мероприятиям.
6. **Хук в `/start`** (§5): после `get_or_create_user_by_telegram_id` — вызов отложенного
   матчера. Идёт через `data_controller` (tg-bot.md §9), не прямым ORM из хендлера.

### Что покрыть тестами в первую очередь

- A1/A2/A3 срабатывают только при **уникальном** кандидате; при двух кандидатах — ручная очередь.
- Тёзки (совпало только ФИО) — никогда не автослияние.
- Новый человек в боте с ФИО как у легаси-персоны, но другим телефоном — **не** получает чужую историю.
- Повторный прогон импорта не задваивает `participations` (идемпотентность).
- Сменившийся username: A2 (ФИО+телефон) всё равно сливает; при отсутствии телефона — ручная очередь.
