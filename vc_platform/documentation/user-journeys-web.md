# Пути пользователя — Web Platform / TG Mini App (CJM + User Stories)

> Схематичное описание **всех** путей пользователя на сайте (Web Platform) и в TG Mini App.
> Функционал у них **идентичный** — различается только точка входа и способ аутентификации
> (сайт: логин/пароль; Mini App: Telegram `initData`). Поэтому кейсы общие; где путь
> различается только на входе — это отмечено в шаге.
>
> Формат каждого кейса: **User story** (как <роль> я хочу <цель>, чтобы <ценность>) +
> краткая цепочка **CJM** (точка входа → страница/действие → результат).
>
> Роли аддитивны. Кейсы сгруппированы по уровням: **Гость → Волонтёр → Тим-лидер → Менеджер**.
> Источник: [architecture.md](architecture.md), [access-control.md](access-control.md), [reports.md](reports.md).
>
> Легенда: ✅ happy-path · ⚠️ альтернативный/ошибочный исход · 👁 публичный · 👤 расширенный · 🔒 внутренний · 👥 участники меро.
>
> **Текущая реализация:** сайт реализован как server-rendered Django (сессионная аутентификация),
> роутинг — см. [blog/urls.py](../blog/urls.py). Mini App (`initData`) и JWT — запланированы (Этап 8).

## 0. Гость / неавторизованный

На сайт **нельзя** попасть без аккаунта, созданного через Telegram. Самостоятельной веб-регистрации нет.

### G1. Открытие сайта без входа
**Story:** Как неавторизованный человек я хочу зайти на сайт, чтобы получить доступ к платформе.
**CJM:** Открывает URL → форма логина (`/login/`) с кнопкой `Регистрация` → без валидных кред дальше не пускает.
⚠️ Нет аккаунта → на форме есть кнопка `Регистрация`, которая **перекидывает в Telegram-бота** (deep-link на `/start`); самостоятельной веб-регистрации нет, аккаунт создаётся только через бота (см. bot G4/V11).

### G2. Вход по логину/паролю (Web Platform)
**Story:** Как волонтёр я хочу войти на сайт по паролю, чтобы работать без Telegram/ВПН.
**CJM:** `/login/` → вводит `login` + `password` → бэкенд проверяет `password_hash` → сессия/JWT → редирект на дашборд.
⚠️ Неверные креды → ошибка на форме. Пароль не задан (не касался бота) → войти нельзя, нужно задать через бота.

### G3. Вход в Mini App (Telegram)
**Story:** Как волонтёр я хочу открыть Mini App в Telegram, чтобы сразу попасть в свой аккаунт.
**CJM:** Открывает Mini App из бота → Telegram `initData` проверяется на бэкенде → тот же аккаунт, тот же функционал, без пароля.

### G4. Выход
**Story:** Как пользователь я хочу выйти, чтобы завершить сессию.
**CJM:** Меню → `Выход` (`/logout/`) → сессия/refresh-токен отзывается → форма логина.

## 1. Волонтёр

Базовый доступ. Видит публичные данные всех и полный доступ к своему аккаунту.

### V1. Лента / список мероприятий
**Story:** Как волонтёр я хочу открыть ленту меро, чтобы выбрать, куда пойти.
**CJM:** Меню → `Мероприятия` (`/events/`) → список карточек (👁 публичные поля).

### V2. Публичная карточка мероприятия
**Story:** Как волонтёр я хочу открыть карточку меро, чтобы прочитать детали.
**CJM:** В ленте → карточка (`/events/<id>/`) → 👁 название, описание, даты/время, локация, организация, категории, статус набора/меро, требования, ТЛ, ссылка на пост, people_helped.

### V3. Подача заявки на мероприятие
**Story:** Как волонтёр я хочу подать заявку с сайта, чтобы участвовать.
**CJM:** Карточка меро → форма заявки (`/applications/new/`) → отправка → `applications(status='new')`, уведомление ТЛ/менеджеру.
⚠️ Набор закрыт / аккаунт заблокирован → соответствующая ошибка (правила как в боте V4).

### V4. Расширенная карточка меро (👥 участник)
**Story:** Как участник я хочу видеть детали своего меро (чат, письмо, рейтинг), чтобы пользоваться ими.
**CJM:** Карточка меро, где волонтёр участвовал → доп. блок: кол-во волонтёров, ссылка на чат, Добро.ру, средний рейтинг, благодарственное письмо, CTA оценить.
⚠️ Не участвовал → расширенный блок скрыт.

### V5. Оценка мероприятия (CTA)
**Story:** Как участник я хочу оценить меро и оставить комментарий, чтобы дать обратную связь.
**CJM:** Расширенная карточка → CTA «оставить оценку» (`/events/<id>/feedback/`) → рейтинг 0–10 + комментарий → `event_feedbacks`.
⚠️ Уже оценивал → форма не показывается.

### V6. Свой публичный профиль (👁)
**Story:** Как волонтёр я хочу видеть свой публичный профиль, чтобы понимать, что видят другие.
**CJM:** Меню → `Профиль` (`/profile/<id>/`) → 👁 ник, часы/меро (всего+сезон), список прошедших меро, «Звёздочка ⭐».

### V7. Свой расширенный профиль (👤)
**Story:** Как волонтёр я хочу видеть свои личные данные и историю, чтобы управлять ими.
**CJM:** `/profile/<id>/` (владелец) → 👤 ФИО, контакты, возраст/пол, полная история заявок, любимые категории.
> Благодарственные письма в расширенном профиле не показываются — они доступны в карточке соответствующего меро (V4/V8).

### V8. Скачивание благодарственного письма
**Story:** Как волонтёр я хочу скачать благодарственное письмо за меро, чтобы использовать его (ПГАС).
**CJM:** Расширенная (участник) карточка меро → «Скачать письмо» (`/events/<id>/letter/`) → PDF генерируется на лету подстановкой ФИО в шаблон `events.letter_id`.
⚠️ У меро не задан `letter_id` → письма нет.
> Письмо доступно только в апп/на сайте (Mini App / Web), из карточки меро. В расширенном профиле писем нет.

### V9. Просмотр чужого публичного профиля
**Story:** Как волонтёр я хочу видеть публичные профили других, чтобы видеть сообщество/топы.
**CJM:** Из ленты/меро → чужой профиль → только 👁 уровень (без контактов/внутренних данных).

### V10. Редактирование личных данных
**Story:** Как пользователь/волонтёр я хочу редактировать свои личные данные (номер, ФИО, telegram username, email, VK, о себе, ДР), чтобы профиль был полным и актуальным.
**CJM:** Свой расширенный профиль → `Редактировать` (`/profile/<id>/edit/`) → форма с полями `first_name`, `last_name`, `phone`, `email`, `telegram_username`, `VK_username`, `about`, `birthday`, `gender` → сохранение в `users`.
⚠️ Пустые/некорректные значения (телефон, email) → валидация на форме.
> Путь доступен владельцу профиля на Web и в Mini App (функционал идентичен).

## 2. Тим-лидер

Всё, что у волонтёра + контекстные права по своим меро (`event_staff.staff_role='team_lead'`).

### TL1. Внутренняя карточка своего меро (🔒 контекстно)
**Story:** Как ТЛ я хочу видеть набор и заявки по своему меро, чтобы управлять командой.
**CJM:** Карточка своего меро → 🔒 блок: статистика набора (нужно/есть/осталось), список заявок с фильтрами, контакты команды, внутренние комментарии.
⚠️ Чужое меро → внутренний блок скрыт.

### TL2. Обработка заявок (approve/reject)
**Story:** Как ТЛ я хочу одобрять/резервировать заявки своего меро, чтобы набрать команду.
**CJM:** Список заявок меро → по заявке `Одобрить` / `В резерв` (`/applications/<id>/process/`) → `approved` (авто-`participations` на все дни) / `rejected`; пересчёт `recruit_status`.

### TL3. Простановка явки
**Story:** Как ТЛ я хочу отметить явку участников, чтобы начислить часы.
**CJM:** Карточка дня меро → редактирование участия (`/participations/<id>/edit/`) → `attended` / `absent_excused` / `absent_unexcused` + часы → пересчёт агрегатов и churn.

### TL4. Ручное начисление churn
**Story:** Как ТЛ я хочу отметить недобросовестность волонтёра моего меро, чтобы это учлось.
**CJM:** Профиль/участие волонтёра моего меро → действие churn → `users.churn_score += penalty`.

### TL5. Контекстный доступ к профилю волонтёра (👤/🔒)
**Story:** Как ТЛ я хочу видеть расширенный+внутренний профиль кандидата, чтобы оценить его.
**CJM:** Профиль волонтёра, подавшего/участвующего в моём незавершённом меро → 👤 и 🔒 уровни открыты (правило 5).
⚠️ Меро завершено / волонтёр не связан → доступ закрыт, только 👁.

### TL6. Комментарий волонтёру
**Story:** Как ТЛ я хочу оставить заметку о волонтёре моего меро, чтобы зафиксировать.
**CJM:** Профиль волонтёра (контекст) → добавить комментарий (`/profile/<id>/comment/`) → `user_comments`. Волонтёр не видит.

### TL7. Оценка/комментарий организации (после своего меро)
**Story:** Как ТЛ я хочу оценить организацию после проведённого меро, чтобы копить историю.
**CJM:** Карточка организации своего меро → рейтинг + комментарий → `organizations.internal_rating/comment`.
⚠️ Организация, с которой ТЛ не проводил меро → недоступно.

### TL8. Управление требованиями/исключениями своего меро
**Story:** Как ТЛ я хочу задать требования и исключения по своему меро, чтобы фильтровать заявки.
**CJM:** Внутренняя карточка меро → требования (`event_requirements`) и исключения (`user_requirement_exceptions`).

## 3. Менеджер

Полный доступ ко всем данным и управляющим действиям. Точки входа — весь сайдбар.

### M1. Дашборд
**Story:** Как менеджер я хочу видеть сводку, чтобы держать руку на пульсе.
**CJM:** Вход → дашборд (`/`) → ключевые показатели/ссылки на разделы.

### M2. Создание и публикация мероприятия
**Story:** Как менеджер я хочу создать и опубликовать меро, чтобы объявить набор.
**CJM:** `Мероприятия` → `Создать` (`/events/new/`) → заполняет поля (в т.ч. категории из выпадающего списка и тип учёта Добро.ру: `none` / `shared` — выбор общей ссылки / `unique` — ввод своей ссылки) → добавляет дни (`/events/<id>/days/add/`) → назначает персонал (`/events/<id>/staff/assign/`) → `Опубликовать` (`/events/<id>/publish/`) → `published_at`, рассылка через очередь → бот.

### M3. Редактирование мероприятия
**Story:** Как менеджер я хочу править меро, чтобы актуализировать данные.
**CJM:** Карточка меро → `Редактировать` (`/events/<id>/edit/`) → сохранение.

### M4. Назначение тим-лидера/менеджера на меро
**Story:** Как менеджер я хочу назначить ТЛ/менеджера на меро, чтобы распределить ответственность.
**CJM:** Карточка меро → `Назначить персонал` (`/events/<id>/staff/assign/`) → запись `event_staff`.

### M5. Внутренняя карточка любого меро (🔒)
**Story:** Как менеджер я хочу видеть полную внутреннюю карточку любого меро, чтобы контролировать.
**CJM:** Карточка меро → 🔒 набор, все заявки, контакты команды и организатора, Добро.ру, шаблон письма, внутренние комментарии.

### M6. Обработка заявок и явки на любом меро
**Story:** Как менеджер я хочу обрабатывать заявки/явку везде, чтобы подстраховывать.
**CJM:** Как TL2/TL3, но без контекстного ограничения — на всех меро. Плюс очередь заявок (`/applications/pending/`).

### M7. Импорт заявок из Excel
**Story:** Как менеджер я хочу массово загрузить заявки из Excel, чтобы не вводить вручную.
**CJM:** `Импорт` (`/applications/import/`) → загрузка `.xlsx` → превью (создать/обновить/ошибки, авто-создание меро для ненайденных) → `Подтвердить` (`/applications/import/commit/`) → коммит + отчёт.
⚠️ Ошибки/дубли в файле → показываются в превью до коммита.

### M8. Список пользователей и внутренний профиль (🔒)
**Story:** Как менеджер я хочу видеть всех волонтёров и их внутренние данные, чтобы управлять.
**CJM:** `Пользователи` (`/users/`) → профиль (`/profile/<id>/`) → 🔒 статус, churn (+`churn_history`), исключения, конверсия, динамика, комментарии.

### M9. Ручное редактирование часов/статистики
**Story:** Как менеджер я хочу поправить часы волонтёра вручную, чтобы исправить ошибки.
**CJM:** Профиль/участие → ручное редактирование `participations.hours` / `users.*_hours`.

### M10. Смена статуса волонтёра (active/blacklisted)
**Story:** Как менеджер я хочу заблокировать/разблокировать волонтёра, чтобы регулировать доступ.
**CJM:** Внутренний профиль → смена `users.status` (при blacklisted — инвалидация веб-сессий).

### M11. Комментарий волонтёру (любому)
**Story:** Как менеджер я хочу оставить заметку о любом волонтёре, чтобы копить контекст.
**CJM:** Профиль → комментарий (`/profile/<id>/comment/`) → `user_comments` / `users.comment`.

### M12. CRUD организаций
**Story:** Как менеджер я хочу вести справочник организаций, чтобы привязывать меро.
**CJM:** `Организации` (`/organizations/`) → `Создать` (`/organizations/new/`) / карточка (`/organizations/<id>/`) → 🔒 профиль, статистика, меро, категории, организаторы, рейтинг, комментарии.

### M13. CRUD организаторов + история взаимодействия
**Story:** Как менеджер я хочу вести контактных лиц и логировать общение, чтобы не терять договорённости.
**CJM:** `Организаторы` (`/organizers/`) → `Создать` (`/organizers/new/`) / карточка (`/organizers/<id>/`) → 🔒 контакты, привязки, `organizer_interaction_log`.

### M14. Отчёт за период
**Story:** Как менеджер я хочу удобно выбирать период отчёта — заготовленными датами (неделя / месяц / сезон) или вручную через выпадающий календарь, — чтобы анализировать и отчитываться.
**CJM:** `Отчёты` → `За период` (`/reports/period/`) → выбор периода: пресеты `[Неделя] [Месяц] [Сезон]` **или** ручной диапазон (дата начала — дата конца) через выпадающий календарь → блоки: общие достижения, воронка, эффективность набора, нагрузка персонала, retention/churn, проблемные зоны, сравнение периодов, графики.

### M15. Экспорт отчёта (Excel / PDF / комплексный)
**Story:** Как менеджер я хочу выгрузить отчёт за период в Excel и оформленный PDF, чтобы передать руководству/грантодателям.
**CJM:** Отчёт → `Экспорт` (`/reports/period/export/`) → выбор формата:
- `Excel-отчёт за период` (`.xlsx`) — многолистовая машиночитаемая выгрузка;
- `PDF-отчёт за период` (`.pdf`) — оформленный человекочитаемый документ с графиками;
- `Комплексный отчёт за период` — Excel + PDF одним пакетом.
> Подробный состав, макет и примеры каждого файла — в [reports_template.md](reports_template.md); формулы метрик — в [reports.md](reports.md) §7.

### M16. Управление сезонами и константами
**Story:** Как менеджер я хочу задавать даты сезонов и значения `const`, чтобы настраивать бизнес-правила.
**CJM:** `Настройки` (`/settings/`) → сезоны (даты) + константы (churn-пороги, ПГАС, множитель набора и т.д.).
⚠️ Сезон истёк, следующий не задан → плашка «задайте дату конца сезона»; закрытие сезона запускает churn-carryover и обнуление `season_*`.
> ⚠️ Управление сезонами через UI и вызов `close_season` по расписанию — частично не реализованы. См. вопросы.

### M17. Отчёт простановки часов на Добро.ру
**Story:** Как менеджер я хочу удобный отчёт, кому/сколько/куда проставлять часы на Добро.ру, чтобы вручную закрыть простановку без ошибок и ничего не забыть.
**CJM:** `Отчёты` → `Часы на Добро.ру` (`/reports/dobro/`) → выбор периода и фильтров → переключатель разреза `[По человеку] [По ссылке]`:
- **По человеку** — список волонтёров, под каждым его attended-участия (меро, дата, часы, тип ссылки, сама ссылка) с чекбоксом `Проставлено`; кнопка «Отметить всё».
- **По ссылке** — группировка по `shared`/`unique` ссылке → меро → волонтёры, прогресс «X из N», кнопка «Отметить всю ссылку проставленной».
→ отметка пишет `participations.dobro_ru_logged=true` (+`logged_at/by`); при полном закрытии меро пересчитывается `events.dobro_ru_hours_logged`.
⚠️ Меро с `dobro_ru_link_kind='none'` в отчёт не попадают (в шапке видно, сколько исключено).
> Разрезы и примеры — [reports.md](reports.md) §8.

## 4. Сквозные / системные пути

### S1. Первый вход на сайт после установки веб-кред в боте
**Story:** Как волонтёр я хочу впервые войти на сайт после того, как задал пароль в боте.
**CJM:** Бот (V11) → `set-web-credentials` → сайт `/login/` → вход → тот же аккаунт.

### S2. Инвалидация сессии при смене пароля/блокировке
**Story:** Как система я хочу разлогинить пользователя при смене пароля или блокировке, для безопасности.
**CJM:** Смена пароля через бота (V12) или blacklist менеджером (M10) → все refresh-токены/сессии отзываются → на сайте требуется повторный вход.

### S3. Синхронность данных между каналами
**Story:** Как пользователь я хочу видеть одни и те же данные в боте и на сайте, чтобы не путаться.
**CJM:** Любое действие (заявка/явка/статус) в одном канале → сразу отражается в другом (единая БД через `data_controller`).
